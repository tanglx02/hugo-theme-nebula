# Hugo 主题 Nebula v1.0.5 验收报告

- **仓库**：https://github.com/tanglx02/hugo-theme-nebula
- **版本**：v1.0.5（发布门禁 + 测试覆盖修复）
- **基线**：v1.0.4（`86f1193`）
- **验收日期**：2026-10-08
- **验收环境**：Hugo extended v0.167.0（windows/amd64）、Python 3.13、Playwright（Chromium / Firefox / WebKit）、GitHub Actions ubuntu-latest

---

## 一、本轮定位

v1.0.4 解决了"测试脚本打印 FAIL 但 exit 0"的假绿问题，但**门禁本身的覆盖面仍有缺口**。
本轮不做新功能，只做三件事：

1. 把发布门禁从"看起来全站"变成"证明是全站"；
2. 修掉一个真实的用户可见缺陷（复制失败被提示成成功）；
3. 给 i18n 加静态防回归，避免文案重新被写死。

所有结论都用**故意注入缺陷 → 确认 CI 真实变红**的方式验证，不接受"改测试让它变绿"。

## 二、修复的真实缺陷

### 2.1 复制超时被伪装成成功（用户可见）

**问题**：`assets/js/main.js` 中代码块复制的实现里，
`navigator.clipboard.writeText()` 返回的 Promise 若长时间不 settle，400ms 后走 fallback；
而 fallback 里 `document.execCommand('copy')` **不检查返回值**就直接调用成功回调。

结果：在剪贴板被拒绝、权限缺失、或 execCommand 失败的场景下，**复制实际失败，界面却提示"已复制"**。
用户会据此认为链接/代码已复制成功，粘贴时才发现是旧内容。

**修复**：抽出统一的 `copyText(text, cb)`，结果只有成功/失败两种：

| 场景 | 修复后行为 |
| --- | --- |
| `writeText` resolve | 成功 |
| `writeText` reject | 走 fallback |
| `writeText` pending > 1200ms | 走 fallback，**绝不显示成功** |
| 无 Clipboard API | 走 fallback |
| `execCommand('copy')` 返回非 `true` | **失败**，显示"复制失败，请手动复制" |

配套改动：

- 超时阈值 400ms → 1200ms（给真实浏览器更多机会）；
- 代码块复制、分享"复制链接"、微信复制统一到同一实现；
- 新增 `common.copyFailed` 文案（zh-CN / zh-TW / en 三语言齐全）；
- 新增 `.copy-failed` 样式，失败态与成功态视觉可区分。

### 2.2 Release 全站审计实际漏掉 20% 的页面

**问题**：v1.0.4 的 `AUDIT_FULL=1` 在枚举 sitemap 时排除了 taxonomy 与 page 类页面，
并且 Hugo 的 sitemap **本身就不包含 `/page/N/`**。实际结果：sitemap 有 122 个 HTML 页面，
审计只跑了 105 个，**分类 term 页、标签 term 页、分页页全部没被审计**。

更严重的是它**没有对此做任何断言**——页面数少了 17 个，审计依然报"全站通过"。

**修复**：

- 取消 taxonomy / page 排除；
- Hugo sitemap 不含分页，改为沿站点真实链接多轮抓取 `/page/N/` 并单独计数；
- 新增两条硬断言：
  - **数量一致**：`sitemap_html + extra_pagination == audited_html`；
  - **类型齐全**：分类 term / 标签 term / `page/2/` / `page/3/` / 分类首页 / 标签首页 /
    归档页 / 文章页，任一缺失即失败。

**当前覆盖**：122（sitemap）+ 3（分页）= **125 个 HTML 页面**，加 1 个 404 探针 = 126 个 URL。

### 2.3 白名单宽松匹配会造成假绿

**问题**：故意缺失的测试资源（`/not-exist.png`）用 pathname 精确匹配豁免，这是对的。
但需要验证"精确"这件事是否真的有价值——如果换成 `endswith` 会怎样？

**A/B 对照实验**（同一份产物，只改匹配规则）：

| 规则 | 审计结果 |
| --- | --- |
| `endswith`（宽松） | `TOTAL PROBLEMS: 0` → **假绿** |
| pathname 精确匹配 | `3 个 broken-image` → **正确判红** |

因为注入的真实损坏资源路径是 `/images/not-exist.png`，`endswith("/not-exist.png")` 会把它一并豁免。

### 2.4 CI 偶发误报：lazy image 判定（两次修复才根治）

v1.0.5 新增的懒加载审计首次接入 CI 后，**webkit job 出现偶发失败**：

```
FAIL  [webkit] 375px × 22 页 :: 2 个问题
FAIL  [webkit] 768px × 22 页 :: 1 个问题
### webkit / image-not-loaded  x3
     375px / :: 1 张图片在滚动触发懒加载后仍未完成
```

本地**完全无法复现**（连续多次运行均在 0.02s 内完成），确认是 CI 环境特有的时序问题。

**第一次修复（仅缓解）**：`settle_lazy_images()` 的执行顺序错了 ——

```python
page.wait_for_function("...every(i => i.complete)", timeout=8000)   # 可能超时
pending = page.evaluate("...filter(i => !i.complete).length")        # ← 立刻采样
page.wait_for_load_state("networkidle", timeout=3000)               # ← 网络静默在采样之后
```

等于"**等完网络，却用等待之前的旧快照下结论**"。改为先等 `networkidle` 再采样，
并复查一轮。CI 误报从 3 次降到 1 次 —— **缓解了，但没根治**。

**第二次修复（根治）**：注入一张挂起图片，同时打印页面全部图片状态，發現真正的元凶：

```
total: 17  notComplete: 0
complete但naturalWidth=0: ['']        ← src 为空
BAD: {'src': '', 'complete': True, 'nw': 0, 'loading': None}
```

定位到灯箱的占位元素：

```html
<div class="lightbox" id="lightbox" ...>
  <img alt="">          <!-- 没有 src -->
```

这个 `<img>` 的真实地址由 `main.js` 打开灯箱时填入。它没有 src，
**webkit 下 `complete` 长期为 `false`**，于是被审计脚本当成"滚动后仍未加载的懒加载图片"。

两处修复：

1. **`audit.py`**：只统计**真正会发起网络请求**的图片 —— 要求有非空 `src`/`currentSrc`
   且有布局尺寸；同时要求 `complete && naturalWidth > 0`
   （`complete` 为 true 不等于已解码出实际宽度）；
2. **`baseof.html`**：灯箱占位图改用 1×1 透明 GIF data URI，
   既消除无 `src` 的非规范 HTML，也让该元素立即 `complete`。

**每一层修复都必须双向验证**——只证明"不再误报"是不够的，还要证明"没有掩盖真实缺陷"：

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 正常页面（含灯箱空 img、无布局盒图片） | `settle = 0` | `0` |
| 注入真实挂起图片（有 src + 200×100 布局盒 + HTTP 端点永不响应） | `settle > 0` | `1` |
| `verify_lightbox.py`（占位图是否破坏灯箱功能） | 全通过 | `21/21` |
| 本地 chromium / webkit / firefox 审计 | 全绿 | 全绿 |

> 验证挂起图片时踩过两个坑：
> ① 用 Playwright `route` 拦截并返回空响应，会让图片立即进入 error 状态
> （`complete=true`），"注入的缺陷测不出来"；须用真实的挂起 HTTP 端点。
> ② 注入图片若没有布局盒（尺寸 0×0），按新判据会被跳过 —— 这是**正确行为**，
> 但做测试时必须给它显式尺寸，否则会误以为"检测失效"。

## 三、新增门禁

### 3.1 `tools/verify_copy.py`（复制语义，13 例）

对代码块按钮、分享按钮、微信按钮分别验证 A–G 七类场景：resolve / reject / pending 超时 /
无 Clipboard API + fallback 成功 / fallback 失败 / 文案恢复。

期望文案**不写死**，从页面注入的 `window.NEBULA_I18N` 读取，因此可配合任意语言构建运行。

已接入 `browser-tests`（三浏览器）与 `release-full-audit`（三浏览器）。

### 3.2 `tools/check_i18n_hardcode.py`（i18n 静态防回归）

扫描 `layouts/**/*.html` 与 `assets/**/*.js`，命中 36 个禁用 UI 文案即失败。
注释、`i18n` 调用本身、README 除外。

两个关键设计：

- **扫描到 0 个文件时同样 `exit 1`** —— 不会因路径解析错误而静默通过；
- 主题目录按 `命令行参数 > NEBULA_THEME_DIR > 仓库根 > 站点主题副本` 依次探测，
  全部候选都不合格时报错退出。

> 这条检查在接入 CI 时立刻暴露了一个真问题：初版默认路径硬编码为
> `../myblog/themes/hugo-theme-nebula`，在 CI 上不存在，会必然失败。已改为自动探测。

### 过程中发现并修正的自身失误

第一轮恢复注入时用了 `git checkout -- <file>`，但注入提交已在历史中，
checkout 恢复到的是**已提交的注入版本**而非修复版本，导致后续 run 出现残留失败。
第二次改用 `git revert` 后又发现：`revert` 作用于整个历史，
撤销注入时会连带回退同一文件里的真实修复（`main.js` 的超时语义、`share.html` 的 i18n 调用）。

**最终处理**：从站点侧修复版重新同步这两个文件，并补一次完整本地回归确认。
教训记录：注入实验的恢复必须用 revert 提交而非工作区 checkout，且 revert 后要逐文件核对修复代码是否在位。

## 八、已知限制

1. **Release 全站审计耗时**：三浏览器 × 四视口 × 126 URL，GitHub Actions 上约 8–12 分钟。
   已设置 `timeout-minutes: 90`，`fail-fast: false` 保证三浏览器结果都能看到。
2. **`/not-exist.png` 白名单是精确单条**：新增其它"故意缺失"夹具时，
   必须同步在 `INTENTIONAL_MISSING_PATHS` 中登记完整 pathname，否则会被判为缺陷。
   这是刻意的——宁可误报也不误豁免。
3. **i18n 硬编码检查是词表驱动**：36 个禁用词覆盖当前 UI 文案。
   未来新增 UI 文案若用了词表外的中文串，需同步扩充词表。
4. **本地测试需注意服务器缓存**：复用旧的 `serve.py` 进程会读到过期产物
   （`SimpleHTTPRequestHandler` 不会感知文件变化）。改完主题务必重启服务器，
   否则会得到"注入没被抓到"的错误结论——本轮已踩过这个坑。
