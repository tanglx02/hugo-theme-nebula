# DEVELOPMENT_WORKFLOW — 开发流程（从需求到合并）

> 本文件描述 Nebula 项目**实际采用并有证据支撑**的开发流程，以及从中提炼的、
> 可移植到其它 Hugo 主题项目的做法。证据来源：Git 提交历史、CI 配置、`docs/` 各阶段交接报告。

---

## 1. 总览：七阶段流水线

```
① 需求分析 → ② 架构设计 → ③ 编码 → ④ 构建 → ⑤ 测试 → ⑥ 文档 → ⑦ 提交 PR
                 ↑                                    │
                 └────────── 故障注入自证（回环）────────┘
```

每个阶段的**进入条件 / 产出 / 出口条件**如下。

| 阶段 | 进入条件 | 产出 | 出口条件（可判定） |
| --- | --- | --- | --- |
| ① 需求分析 | 有明确的需求或缺陷报告 | 需求条目 / 功能缺口编号（如 M16） | 需求可被拆成可验证断言 |
| ② 架构设计 | 需求确定 | 落点设计（改哪个 partial / 是否新增单点配置入口）、向后兼容策略 | 明确「默认是否改变站点 URL 结构」 |
| ③ 编码 | 设计确定 | 模板 / CSS / JS 改动 | 本地 `hugo` 构建 rc=0 |
| ④ 构建 | 代码就绪 | `public/` 产物 | 五版本构建 rc=0、ERROR=0 |
| ⑤ 测试 | 产物就绪 | 门禁结果（真实退出码） | 相关门禁 rc=0 **且经故障注入证明可失败** |
| ⑥ 文档 | 测试通过 | README / CHANGELOG / 文档更新 | `check_docs.py` 通过 |
| ⑦ 提交 PR | 全部通过 | 分支 + PR | CI 全绿（含三浏览器） |

---

## 2. 各阶段的实操要点

### ① 需求分析

- 需求要么来自**明确的产品诉求**，要么来自**独立验收报告**中的条目（本项目存在多轮独立第三方测试）。
- 每个需求/缺陷必须有**唯一编号**（如 `BUG-P1-003`、`TEST-DEFECT-R2-007`、`M16`），
  并在 `docs/final-cleanup-issue-tracker.md` 登记：原 ID / 问题 / 现状 / 证据 / 结论。
- **编号是一次性分配的，永不复用**：历史条目即使已修复也**保留**（只追加「结论」），
  避免「编号漂移导致追溯断裂」。

### ② 架构设计

设计阶段必须回答三个问题（本项目的硬性要求）：

1. **默认行为是否改变？** 若改变站点 URL 结构 / 产物，需明确是否属破坏性变更。
   → 经验：M16 作者档案页最初因「担心 `taxonomies.authors` 改变默认 URL」被列为限制；
   最终用**可选启用 + 不注册 taxonomy 时零改变**化解。
2. **是否新增「单点配置入口」？** 复杂功能应收口到一个 `util/*.html`（见 PROJECT_OVERVIEW §3.3）。
3. **向后兼容如何证明？** 需要可执行的对照（如 BC1：与「无本功能」基线主题规范化后逐字节比较）。

### ③ 编码

- 模板不得写死 UI 文案（走 `i18n`）；不得内联危险 scheme；不得就地重复实现单点工具。
- 新增/修改建议遵循现有 partial 命名与目录约定。

### ④ 构建

```bash
# 生成压力/边界夹具（含 zz-* 边界文章、图片 bundle、多 section）
python3 tools/gen_testdata.py --posts-dir exampleSite/content/posts

# 生产构建
hugo --source exampleSite --themesDir ../.. --gc --minify -d ../public
```

- **构建必须逐版本验证**（本地 5 版本 + CI 含 `latest`）。
- 若涉及图片管线，必须装 `Pillow`，否则 `render-image` 的处理分支**永远不会被构建到**（历史教训）。

### ⑤ 测试（本项目最重的环节）

三条铁律：

1. **门禁「失败即 `exit ≠ 0`」**：不存在「打印 FAIL 但退出 0」（统一走 `tools/_testlib.py` 的 `Harness`）。
2. **重要门禁必须经故障注入自证**（见 §3）。
3. **构建型门禁在本地须前台运行**（本环境后台运行会被 `safe-delete` 守卫伪打断，见 §5）。

### ⑥ 文档

- 受 `check_docs.py` 约束：README 关键表述、CHANGELOG 条目、版本号一致性。
- 文档改动**不得引入绝对化表述**（「零 X」「永远」），除非有确定性依据。

### ⑦ 提交 PR

- 分支命名：`feat/...`、`fix/...`。
- 提交信息用**中文 + 前缀**（`feat(scope):` / `fix(scope):` / `test:` / `ci:` / `docs:`）。
- PR 前确认：CI 全绿、无 force-push、未改写 `main`。

## 3. 故障注入自证（本项目的核心方法论）

**原则：一个门禁如果从未红过，就不算被验证过。**

流程（每一步都要留证据）：

```
备份 → 注入缺陷 → 跑门禁 → 确认 rc≠0（且失败信息指向被注入处）
     → 还原 → 回读核验（git diff）→ 复跑确认回绿
```

已固化的注入：

| 门禁 | 注入 | 结果 |
| --- | --- | --- |
| `check_ci_jobs.py --selftest` | 8 类（删步骤 / 步骤 if:false / job if:false / continue-on-error / echo 空转 / 单引擎 / 换矩阵值 / 删搜索多语言环境变量） | 8/8 变红 |
| `check_new_features.py --selftest` | 5 类 | 5/5 变红 |
| `check_index.py` | 截断索引正文 | 末尾标记消失 → 判红 |
| `verify_baseurl.py --selftest-exitcode` | 假 hugo（非零码 + 残留产物） | 断言「绝不读残留产物」→ 判红 |
| `check_author_pages.py` | 关站点开关 / `.author-link` 退回 inline | 6 条 / 2 条变红 |

> **教训**：注入必须**彻底破坏判据**。用子串匹配时，`home-profile-BROKEN` 仍包含
> `home-profile`，弱注入不会变红——这会把「注入方法问题」误判为「测试假绿」。
> 详见 `TESTING_FAILURES.md`。

## 4. 迭代与冻结规则

- **一次只做一件事**：修复轮只修报告列出的项，不做「顺手重构」。
- **冻结后只做门禁级修复**：功能冻结后只允许「修复可复现、影响实际使用的问题」，
  不允许新增功能 / 重写测试框架 / 为提高数字加用例。
- **SHA 固定**：独立验收、CI 复核、报告引用都必须锚定**完整 40 位 SHA**，
  且明确「该 SHA 是内容冻结提交还是其后仅文档提交」。

## 5. 本地环境经验（Windows / 沙箱）

【已证实】（本项目反复复现）：

- **后台运行构建型门禁会被 `safe-delete` 守卫伪打断**（`SAFE_DELETE_BULK_CONFIRM_REQUIRED` /
  `Access is denied`，`rc=1` 但**产品无缺陷**）→ 一律**前台**运行。
- `HTTP_PROXY` 若被设置，`curl http://127.0.0.1:...` 会返回 502 → 用 `--noproxy '*'`。
- `Edit`/`Write` 偶发「成功但未落盘」或超时 → 关键文件改动后**回读核验**（`git diff`）。
- repo 内写文件偶发 `PermissionError`（防病毒/索引器短暂锁）→ **带重试**。
- 静态服务器 `tools/serve.py` 易残留孤儿进程 → 审计完成后要显式清理（按端口 / 进程名）。

> 这些是**环境性**问题，不是产品缺陷；报告时必须与产品缺陷分开登记（见 TESTING_FAILURES.md）。

## 6. 可移植 vs Nebula 专属

| 做法 | 可移植性 |
| --- | --- |
| 「失败即非零退出」退出码契约 | ✅ 通用 |
| 故障注入自证门禁 | ✅ 通用 |
| 完整 SHA 固定 + 内容冻结提交语义 | ✅ 通用 |
| 单点配置入口 / 单点工具 partial | ✅ 通用 |
| 「默认零改变」的向后兼容对照（BC1） | ✅ 通用 |
| 四类报告口径（已完成/未完成/失败/跳过） | ✅ 通用 |
| 具体门禁脚本集合、具体 14 job 编号 | ❌ Nebula 专属（应抽象为「构建矩阵 / 静态 / 浏览器 / 全站审计」四类） |
| 具体功能编号 M1–M20、Bug 编号 | ❌ Nebula 专属 |
