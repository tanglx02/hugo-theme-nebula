# SKILL_HANDOFF — 通用 Hugo 主题开发 Skill 制作交接报告

> **文件性质**：本报告是"把 Nebula 项目经验提炼为通用 Hugo 主题开发 Skill"的**主交接文档**。
> **事实分层**：正文中每个关键结论标注 **【已证实】**（有代码/CI/实测支撑）/ **【结论】**（开发方判断）/ **【待验证】**（未经独立验收）。
> **边界声明**：本目录 `docs/skill-source/` 仅用于沉淀经验，**不影响主题运行**；其中的命令与脚本名仅作示例。

---

## 一、这次项目采用了什么开发流程

**【已证实】** 完整流程（7 阶段）：

```
需求澄清 → 架构设计 → 编码 → 构建 → 测试 → 文档 → PR
    ↑                                        ↓
    └──── 故障注入自证（贯穿测试）←── 独立第三方验收 ←── 功能冻结候选
```

各阶段要点：

| 阶段 | 做法 | 关键产物 |
| --- | --- | --- |
| 需求澄清 | 先问边界（默认值/未配置行为/是否破坏 URL 结构/跨版本），再写码 | 明确"不做什么" |
| 架构设计 | 单点配置 partial + 唯一入口；能力探测先于依赖 | `util/*.html` |
| 编码 | 严格反模式清单（bool/`default`、rune 截断、`cond`、scheme 校验…） | 模板改动 |
| 构建 | 多 Hugo 版本矩阵 + 边界夹具 + 图片管线覆盖 | `public/` 产物 |
| 测试 | 分层 L0–L7 + **每条重要断言必须故障注入自证** | 门禁脚本 |
| 文档 | README 配置参考 + CHANGELOG + 稳定基线 + 测试说明 | `docs/` |
| PR | 固定 SHA + CI 证据 + 独立验收 + 交接报告 | PR + 报告 |

**贯穿性原则**：**功能冻结**。一旦成为冻结候选，只修"真正的合并阻断项"，其余一律停止。

## 二、哪些规则最能防止 AI 跑偏

**【结论】** 按实际效果排序（这些是"约束力最强"的规则）：

1. **"不做什么"写在"做什么"前面**。
   AI 的默认失败模式是范围蔓延。把"不新增功能 / 不重构测试 / 不为凑数加用例 / 不做无关重构 / 不改已通过的断言与阈值 / 不动 main / 不移动 tag / 不做破坏性 git 操作"写成硬约束，效果立竿见影。

2. **锚定具体 SHA**，而不是"当前分支/最新代码"。
   没有 SHA，AI 会在你等待证据时悄悄改代码，"验证通过"就失去意义。

3. **要求区分事实与结论**（已证实 / 开发方结论 / 仍待独立验证）。
   AI 倾向把"报告里写过"当成事实。显式分层后，"历史宣称已修复"会被强制回代码复核。

4. **要求可执行证据**（复现步骤 + 实测输出 + 退出码），拒绝"应该没问题"。

5. **要求故障注入自证**：任何新门禁必须证明"坏了一定变红"。
   这条规则逼着 AI 从"写断言"升级为"验证断言有效"。

6. **禁止为通过而放宽**：不允许删测试、降阈值、跳过检查、加 `continue-on-error`。

7. **明确停止条件**：报告交付后立即停止，不自行开启新任务。

## 三、如何约束 AI 不无限扩展功能 / 反复改测试

**【结论】** 三个机制：

### 3.1 冻结 + 阻断项白名单

冻结候选后，**只有满足以下之一**才允许改动：

1. 候选 SHA 缺乏完整 CI 证据；
2. 构建/核心功能/兼容测试失败；
3. 历史高优先级产品缺陷复现；
4. PR 有真实冲突或必需检查失败；
5. 存在影响交付判断的严重假绿门禁。

每处修改必须给出：**复现 → 影响 → 根因 → 最小修复 → 验证**。
非以上情形 → 立即停止。

### 3.2 测试"只准变强，不准变弱"

- 允许：新增断言、新增注入、修复假绿/假红。
- 禁止：为让门禁通过而删断言、放宽阈值、改判定逻辑的严格性。
- 若发现某断言是"假绿"，正确动作是**加强它并注入自证**，不是绕过它。

### 3.3 数量不是目标

把"覆盖面"而非"用例数"作为验收标准。**禁止为凑数加用例**（本项目明确写进约束）。

> **已证实反例**：历史上有 TEST-DEFECT 就是因为"断言数量增加但强度没增加"（如 `check_ci_jobs` 只比数量），后来改为**结构级校验 + selftest**。

## 四、如何让新的 AI 快速理解项目状态与历史决策

**【结论】** 一套"三份必读 + 状态锚点"的机制：

| 资料 | 作用 | 本项目对应 |
| --- | --- | --- |
| **稳定基线** | 被 CI 真实执行过的**契约清单**（不是愿望） | `docs/稳定基线.md` |
| **测试说明** | 每个门禁测什么、怎么跑、失败意味着什么 | `docs/测试说明.md` |
| **问题追踪表** | 每个历史问题的**当前真实状态 + 证据 + 结论** | `docs/final-cleanup-issue-tracker.md` |
| 状态锚点 | 分支/HEAD SHA/PR/tag 的实时状态 | `git ls-remote` / GitHub |

**关键约定**：

1. 稳定基线开头写"**修改本主题之前先读这份文件**"，并声明"任何一条被破坏，CI 会真的变红"。
2. 问题追踪表要求"**不以最新一份报告为准**"，对每条编号**回当前代码核实**；历史宣称"已修复"**不直接采信**。
3. 所有资料**绑定 SHA**（"最终版本以 `<branch>` tip 上的文件为准"）。

> **通用建议**：新 AI 的第一条指令应是"先读这三份，再回答任何问题"。

## 五、如何区分：真实产品 bug / 测试脚本 bug / CI 环境问题

**【结论】** 这是本项目最高频的判断，给出一套判据表：

| 维度 | 真实产品 bug | 测试脚本 bug | CI 环境问题 |
| --- | --- | --- | --- |
| **在真实浏览器/产物里可见吗** | 是（如 `.author-link` 40×24px） | 否（产物正常，是脚本读错） | 否（本地不重现） |
| **能否本地稳定复现** | 能 | 能（脚本逻辑错） | 常不能（CI 特有） |
| **换引擎/换机器** | 都复现 | 都"复现"（脚本问题与引擎无关） | 只在该 runner/环境复现 |
| **断言错还是实现错** | 实现错 | 断言错（假绿/假红） | 依赖缺失/网络/版本 |
| **修哪里** | 模板/CSS/配置 | 断言/快照/重试 | 安装依赖/固定 runner |

**三个判据细节【已证实】**：

1. **真实浏览器审计 > 静态字符串断言**。
   R5-001（`.author-link` inline 元素 `min-height` 无效）**由真实浏览器发现**，静态断言（"链接存在/指向正确"）抓不到像素高度。同理 R4-007（flex 块级化 23px 触控目标）。

2. **"稳定地坏" vs "偶发"**。
   真实缺陷**稳定复现**；flaky 多为测试写法问题（双读 DOM R4-008、固定 sleep、CSS 过渡中间值）。修法是"一次快照 + 有界重试"，**断言强度不变**。

3. **`exit 0` 但零用例 = 测试 bug（假绿）**。
   不是"产品没问题"，而是"根本没测"。

> **本项目曾把这三类混为一谈**：R4-001/R4-004 表面是"产品/门禁问题"，实为**测试脚本默认路径指向已不存在的目录**（"只在 CI 里能跑"的隐性缺陷）——这是典型的"测试脚本 bug 伪装成环境问题"。

## 六、如何处理 Hugo 版本兼容、i18n、模板 null、短代码、资源管线

**【已证实】** 逐项：

### 6.1 版本兼容
- **能力探测 > 版本硬编码**：解析 `hugo.Version` 的 major/minor，先探测再用。
- **禁止 `cond` 做能力分支**：Go 模板 `cond` **先求值两个分支**，旧版本会因访问不存在的字段而报错。
- **每个版本真实构建**（不是读文档判断）。
- 支持矩阵：0.128.0 / 0.148.0 / 0.162.0 / 0.166.0 / 0.167.0 / latest。
- 能力阈值（见 `HUGO_COMPATIBILITY.md`）：`resources.Publish` 0.166+、`.Language.Locale` 0.158+、`reflect.IsImageResourceProcessable` 0.128 无。

### 6.2 i18n
- UI 文案一律 `i18n/*.yaml`；**扫到 0 个文件也失败**。
- UI 日期 `i18n "common.dateFormat"`；机器格式走白名单。
- **日期本地化在构建期完成**（搜索索引存 `date` 机器 + `dateDisplay` 本地化；前端只原样输出）。
- JS 文案注入 `NEBULA_I18N`。
- 跨版本陷阱：语言键与文件名不匹配 → 旧版本全站空串（BUG-R3-001）；`[languages.*]` 顶层字段弃用 → 用零告警形态。

### 6.3 模板 null / 空值
- `default` **吞显式 false** → 用布尔解析器（返回 `dict`，因为 partial 返回 bool 会被包成 `template.HTML`）。
- `slicestr` **按 rune**，越界 panic 终止整站 → 统一 rune 安全截断（`countrunes` 判断）。
- 未配置 taxonomy → `site.Taxonomies.*` 需 `default dict` 兜底。
- 缺 date → 不输出 `0001-01-01`；空作者 → 省略 author 字段；空正文 → 不显示"0 分钟/0 字"。

### 6.4 短代码
- 参数**转义**（路径特殊字符）、变体**白名单**、URL scheme **校验（含空白绕过）**。
- 零 JS 优先；可交互部分收敛到最小 JS。
- 跨版本矩阵 + 反证 + "禁止混用参数 / 换行绕过不可构造"。

### 6.5 资源管线
- 图片走 Pipeline（`srcset` + 尺寸占位 + `lazy`）；**用 MediaType 白名单**而非 `reflect.IsImageResourceProcessable`。
- **分支覆盖依赖夹具**：无 Pillow → 图片处理分支永不进入构建 → 不兼容长期未被发现。CI 必须断言特征产物（`srcset=`）。

## 七、如何设计能发现假绿的测试

**【结论】** 直接引用 `TESTING_FAILURES.md` 的八类失效 + 检查清单。核心原则四条：

1. **零用例即失败**：断言输入为空时必须红（防空洞真）。
2. **输入非空断言**：先断言"确实扫到了东西"，再断言"东西符合预期"。
3. **故障注入自证**：每条重要断言必须能证明"坏了一定变红"；注入必须**够强**（子串匹配断言不能只在子串周围加字）。
4. **断言落到真实产物**：尺寸/触控目标等断言要落到**构建产物 CSS 规则**，不能只断言"元素存在"。

**反假绿的具体手段**（本项目已用）：
- 末尾标记（`TAILMARKER_*`）检测截断；
- inventory 绑定构建指纹（`build_id`）防跨次复用；
- 配置感知**绑定到本次构建的源根**（`_looks_like_build_source`）；
- CI 结构门禁的 `--selftest`（8 类注入）+ 关键步骤环境变量契约。

## 八、如何让独立测试 AI 只测不改

**【结论】** 四条硬约束：

1. **固定候选 SHA**：第三方拿的是**具体 commit 的产物**，不是"当前分支"，防止测试期间漂移。
2. **职责隔离**：第三方**只输出"问题清单 + 复现方式 + 实测证据"**，**不改代码**。
3. **修复回开发方**：按"最小修复"处理，再交第三方复验。
4. **遗留项单独编号**：每轮收敛（本项目 R2 / R3 系列），不无限循环。

**辅助机制**：
- 交付物 = 产物 + 复现命令 + 文档（不做口头说明）。
- 第三方**不需要也不应该**了解实现细节（避免被实现思路带偏）。
- 明确的"未验证路径"登记要求（防止第三方声称验过不可控项）。

## 九、严格 SHA 固定、证据归档、最终发布门禁

**【已证实】** 三件事：

### 9.1 SHA 固定
- 每次状态核对用 `git rev-parse HEAD` / `git ls-remote`，**不抄旧报告**。
- CI 证据必须**绑定候选 SHA**（本项目曾出现"CI 跑在 `4a4ea01` 而非 `8363d4b`"，因此**重跑**取得同 footprint 证据）。
- PR 的 head SHA 需与候选一致。

### 9.2 证据归档
- 产物 inventory（`html_inventory.json`）作为审计真值。
- 测试输出可机读（`TEST-RESULT: {...}`）。
- 故障注入记录（注入内容 → 哪条断言红 → 还原回绿）。
- 审计报告作为 CI artifact 上传。

### 9.3 最终发布门禁
- **Release 全站审计**：inventory 100% 被审计 + 分页交叉验证 + alias 静态结构（三条独立证据链）。
- **达安全上限即判未完成**（不判 PASS）。
- **合并需所有者授权**（不自合并）；**tag 在合并后决定**；**不动历史 tag**。

## 十一、做通用 Skill 时的"保留"与"不硬编码"

### 11.1 必须保留（否则 Skill 失去价值）

1. 功能冻结 + 阻断项白名单 + 停止条件。
2. 区分 已证实 / 开发方结论 / 待独立验证。
3. 故障注入自证（每条重要断言必须能红）。
4. 退出码约定：失败/依赖缺失/零用例 = 非零退出。
5. SHA 固定 + 证据绑定。
6. 三层证据链（产物真值 / 交叉验证 / 静态补充）。
7. 布尔 `false` 不被吞；rune 安全截断；能力探测禁 `cond`。
8. 安全校验在源头做。
9. 独立测试只测不改 + 无授权不自合并。
10. 未验证项必须登记。

### 11.2 不应硬编码（否则 Skill 僵化）

1. 具体 SHA / PR / CI run id / 版本号。
2. 具体脚本名、夹具名、issue 编号。
3. 具体页面数、索引体积等数值。
4. Nebula 的品牌、布局名、组件清单。
5. 特定的站点配置键（`authors.pages` 等）。
6. 具体的 Hugo 版本列表（应表述为"覆盖最低支持版 + 中间版 + 当前稳定 + latest"）。

## 十二、通用 Skill 建议结构

### 12.1 目录结构

```
hugo-theme-dev/
├── SKILL.md                    # 入口：触发条件、总流程、硬约束摘要
├── workflows/
│   ├── 01-requirements.md      # 需求澄清
│   ├── 02-architecture.md      # 架构与单点配置
│   ├── 03-coding-rules.md      # 反模式清单（bool/rune/cond/scheme…）
│   ├── 04-build.md             # 多版本构建 + 夹具
│   ├── 05-testing.md           # 分层测试 + 故障注入
│   ├── 06-docs.md              # 文档要求
│   ├── 07-release.md           # 冻结→合并→tag→发布
│   └── 08-handoff.md           # 交接报告模板
├── references/
│   ├── hugo-compat.md          # 版本兼容方法论（非版本列表）
│   ├── i18n.md                 # i18n + 构建期本地化
│   ├── template-pitfalls.md    # 模板陷阱（null/false/rune/length）
│   ├── test-failure-modes.md   # 假绿/假红/残留/环境/退出码
│   └── a11y-and-security.md    # 触控目标/焦点/scheme/CSP
├── templates/
│   ├── stable-baseline.md      # 稳定基线模板
│   ├── test-plan.md            # 测试说明模板
│   ├── issue-tracker.md        # 问题追踪表模板
│   ├── open-limitations.md     # 未完成项模板
│   └── handoff-report.md       # 交接报告模板
└── checklists/
    ├── release.md              # 发布检查清单
    └── anti-drift.md           # 防跑偏自检
```

### 12.2 各文件职责

| 文件 | 职责 |
| --- | --- |
| `SKILL.md` | 触发条件、总流程、硬约束摘要；路由到各 workflow |
| `workflows/01-08` | 每阶段：目标、输入、步骤、产出、禁止事项、完成标准 |
| `references/*` | 方法论知识（可迁移的"为什么"），不含项目实例 |
| `templates/*` | 可直接落地的文档骨架 |
| `checklists/*` | 交付前的勾选项 |

### 12.3 触发条件

- "开发 Hugo 主题 / 给主题加功能 / 修主题 bug / 发布主题版本"。
- "评审主题测试是否有效 / 是否存在假绿"。
- "主题交接 / 独立验收 / 功能冻结"。

### 12.4 输入信息（使用前应收集）

1. 主题仓库路径与分支、**目标 SHA**。
2. 支持的 Hugo 版本范围。
3. 站点/内容形态（单/多语言、多 section、规模）。
4. 是否已存在 `stable-baseline` / `test-plan` / `issue-tracker`。
5. 当前阶段（开发中 / 冻结 / 待合并 / 待发布）。

### 12.5 执行步骤（Skill 的主循环）

```
1. 读状态（git ls-remote / 三层文档）→ 报告真实状态，不抄旧报告
2. 判断阶段 → 进入对应 workflow
3. 任何改动前：确认是否属于"阻断项白名单"；否则停止
4. 编码/修复 → 跑分层门禁 → 故障注入自证
5. 文档同步（稳定基线 / 测试说明 / CHANGELOG）
6. 冻结候选 SHA → 归档证据 → 交接报告
7. 停：无授权不合并、不移动 tag、不开新任务
```

### 12.6 禁止事项

- 冻结后扩展功能、重构测试、为凑数加用例、无关重构。
- 为通过而删测试 / 放宽阈值 / 跳过检查 / 加 `continue-on-error`。
- 用 `default` 读布尔；裸 `slicestr`；用 `cond` 做能力探测。
- 动 main / 移动既有 tag / force push / `reset --hard` / `clean -fdx`。
- 把"历史报告说"当事实；把"未验证"当"已验证"。
- 无所有者授权自行合并。

### 12.7 完成标准

- 所有 MUST-RUN 门禁 `exit 0`，且**每条重要断言已通过故障注入自证**。
- 候选 SHA 有**完整 CI 证据**（含 Release 全站审计）。
- 无未解决的合并阻断项。
- 三层文档（稳定基线 / 测试说明 / 问题追踪表）已更新且绑定 SHA。
- `OPEN_LIMITATIONS` 如实登记。
- 交接报告区分事实/结论/待验证。

### 12.8 最小可用版本（MVP）构建顺序

**先做能立刻阻止最常见错误的，后做全面的。**

1. `SKILL.md`（触发条件 + 硬约束 + 停止条件）— **最高优先级**。
2. `references/template-pitfalls.md`（bool/rune/cond/`default`）— 立竿见影，避免致命模板 bug。
3. `references/test-failure-modes.md` + 退出码约定 — 避免假绿。
4. `workflows/07-release.md`（冻结 + 阻断项白名单 + 不自合并）。
5. `workflows/03-coding-rules.md` + `05-testing.md`（故障注入自证）。
6. `templates/stable-baseline.md` + `templates/handoff-report.md`。
7. `references/hugo-compat.md` + `references/i18n.md`。
8. 其余 references/templates/checklists。

> **MVP 的最小闭环**：能阻止 AI"加功能失控 / 假绿通过 / 无授权合并"这三件事，Skill 就已经有价值。
