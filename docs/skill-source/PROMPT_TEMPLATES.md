# PROMPT_TEMPLATES — 可复用提示词模板

> 资料性质：用于通用 Hugo 主题开发 Skill 的经验沉淀。
> 说明：这些模板是从本项目真实使用的指令中提炼的**结构**，去掉项目专有细节后可直接复用。
> 用法：把 `<>` 内容替换为当前项目实际值。**模板只约束"过程"，不预设"答案"。**

---

## 0. 使用原则

1. **约束范围比描述任务更重要**：AI 最容易犯的错不是"做不出来"，而是"做太多"。每个模板都显式写"不做什么"。
2. **要求区分事实与结论**：明确要求标注 **已证实 / 开发方结论 / 仍待独立验证**。
3. **要求可执行证据**：不接受"应该没问题"，要求"复现步骤 + 实测输出 + 退出码"。
4. **锚定 SHA**：涉及状态核对的模板，一律要求**绑定具体 commit SHA**，不用"当前分支"。

## T1. 需求澄清

```
你是 Hugo 主题开发者。我要做一个 <功能名>。

请先用不超过 8 个问题澄清需求，覆盖：
1. 用户可见行为（默认值是什么？未配置时表现？）
2. 配置入口（站点级 / 页面级？键名？）
3. 向后兼容（是否可能改变默认 URL 结构 / 产物？如何保证默认零改变？）
4. 边界与极端输入（空值 / 非法值 / 特殊字符 / CJK）
5. 跨版本要求（最低支持版本？能力探测还是硬依赖？）
6. 无障碍与安全（触控目标 / 键盘 / scheme 校验）
7. 可测试性（用什么产物/断言证明它生效？如何注入故障证明门禁会红？）
8. 明确不做（本轮不覆盖的范围）

在得到我的回答前，**不要写代码**。
```

## T2. 功能开发

```
在 <repo> 上实现 <功能名>，遵循：

【约束】
- 只实现该功能；不重构无关代码、不扩大范围、不改动已通过的测试与阈值。
- 所有时间/日期/文案本地化在**构建期**完成，不留给前端。
- 布尔开关不得用 `{{ .Params.x | default true }}`（会吞掉显式 false），
  必须走项目的布尔解析器。
- 字符串截断必须按 rune（`countrunes`），禁止裸 `slicestr`。
- 跨版本差异先探测再用，**不得用 `cond`** 做能力分支。
- URL 安全校验在**源头**做（拒绝 javascript:/vbscript:/data:非图片）。
- 新功能若可能改变默认产物/URL 结构 → 做成**默认关闭的可选层**，
  并以"与基线主题规范化后逐字节一致"作为回归门禁。

【交付】
1. 代码改动（列出文件）。
2. 新增/扩展的门禁脚本，以及它的**故障注入自证**（注入什么 → 哪条断言变红 → 还原回绿）。
3. 文档更新（README 配置参考 / CHANGELOG）。
4. 验收：本地跑哪些命令、期望输出。
```

## T3. Bug 修复

```
修复 <bug 描述>。

请按以下结构作答，不要跳步：
1. 复现步骤（精确到命令与夹具；给出实际输出与期望输出的差异）
2. 实际影响（谁能遇到？后果？影响面？）
3. 根因（**到代码行**；解释为什么会发生，而不是现象）
4. 最小修复（只改必要的；列出文件与改动点；说明为何不大改）
5. 验证（复现是否消失？是否引入回归？跑哪些门禁？退出码？）

【约束】
- 不得为了让它过而放宽阈值、删测试、跳过检查。
- 若根因是"同类问题只修了一处"，请**扫描所有同根因位置**并说明（本项目曾因此产生回归）。
```

## T4. 测试评审（"这条门禁真的有效吗"）

```
评审以下门禁/测试脚本是否**真的能发现问题**：

<脚本内容或路径>

逐个断言回答：
1. 断言了**什么**？它的输入集合为空时会怎样（是否空洞真）？
2. 有没有**恒真分支**（`if not found: pass`、空集合循环）？
3. 正则**容忍 minify**（去引号）、单引号、无引号写法吗？
4. 配置感知是否**绑定到本次构建的实际源根**？覆盖 `--config` 叠加层了吗？
5. 异步页面是否**一次快照**（判定与报错信息取自同一时刻）？
6. 涉及动画/过渡的度量**先禁用动画**了吗？
7. 依赖缺失是**致命错误**还是被 skip？
8. 子进程 `returncode` 检查了吗？
9. 临时文件**异常路径也清理**了吗？
10. 请给出**一条能让本门禁变红的强注入**（并说明为何它足够强）。

最后给结论：此门禁 **有效 / 有假绿风险 / 有假红风险**，并给出最小修复建议。
```

## T5. 跨 AI / 人员交接

```
请阅读 <repo> 并产出一份交接说明，供**不了解本项目**的 AI/开发者使用。

必须包含：
1. 当前状态：分支、HEAD SHA、与 main 的关系、开放 PR、tag 状态（**以实时 git/GitHub 为准**）。
2. 架构与目录：主题结构、关键单点配置 partial、构建/测试入口。
3. 不可回退契约清单（搜索索引字段、i18n 规则、分页判定、modal 无障碍、安全基线…）。
4. 已知坑与反模式（含"为什么这样写"）。
5. 如何本地验证：命令、依赖、退出码约定。
6. 事实分层：哪些是**已证实**、哪些是**开发方结论**、哪些**仍待独立验证**。
7. 未完成项与接受为限制的项。

要求：不得把"历史报告里说过"当作事实；每条关键结论给出**代码位置或实测证据**。
```

## T6. 功能冻结

```
现在对 <项目> 执行**功能冻结**。

规则：
- 冻结后不再扩展范围、不重构测试框架、不为凑数加用例、不做无关重构。
- 冻结产出一个**固定候选 SHA**，后续所有证据绑定该 SHA。
- 只有在以下"真正的合并阻断项"出现时才允许修改：
  (1) 候选 SHA 缺乏完整 CI 证据；
  (2) 构建/核心功能/兼容测试失败；
  (3) 历史高优先级产品缺陷复现；
  (4) PR 有真实冲突或必需检查失败；
  (5) 存在影响交付判断的严重假绿门禁。
- 每处修改必须给出：复现 / 影响 / 根因 / 最小修复 / 验证。
- 不改 main、不移动既有 tag、不 force push、不做破坏性 git 操作。

先做**状态核对**（fetch → 核对 main/候选/PR/tag/CI 是否与报告一致），
真实状态与旧报告不一致时**以实时结果为准**，不要复制旧报告。
若无阻断项 → 停止开发。
```

## T7. 最终验收

```
对候选 SHA <sha> 执行最终验收，只输出**一份**简洁但完整的交接报告，包含：

1. main / 候选分支 / 相关 PR 的真实状态（含实时 SHA）。
2. 最终候选 SHA 及其 **CI 链接**与结论。
3. 是否存在**合并阻断项**（逐条对照阻断项定义）。
4. 旧 PR 是否已关闭（如无权限，明确说明）。
5. 是否已合并（**无所有者授权不得自合并**）。
6. 产出文件与其路径。
7. **尚未独立验证**的内容与**接受为限制**的项。
8. 建议的通用主题开发 Skill 结构。
9. 明确最终状态：`READY_TO_MERGE` / `BLOCKED` / `MERGED`。

【停止条件】候选满足合并要求、交接资料整理完毕、报告交付后**立即停止**，
不得自行开启新的开发任务。报告须区分"已证实事实 / 开发方结论 / 仍待独立验证"。
```

---

## T8. 故障注入自证（可嵌入 T2/T4）

```
对门禁 <脚本> 做故障注入自证，逐步执行：
1. 备份目标文件。
2. 注入一个**必然破坏该契约**的改动（注意：注入必须足够强；
   若断言是子串匹配，不要只在子串周围加字）。
3. 运行门禁，**确认退出码 ≠ 0**，且报错指向正确的断言。
4. 还原，回读核验还原成功。
5. 复跑确认回绿。

输出：注入内容、注入后结果（哪几条断言红）、还原后结果、退出码。
若注入后**没有变红**，说明该断言可能是**假绿**，请分析原因（并区分
"测试假绿"与"注入方法太弱"）。
```
