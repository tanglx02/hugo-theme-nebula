## 一、本轮修复的覆盖盲区

### 问题

v1.0.6 用「sitemap + pagination」推算"全站"：

| 数据 | v1.0.6 | 实际 |
| --- | --- | --- |
| sitemap HTML | 122 | 122 |
| audit 审计页数 | 125 | 125 |
| **构建产物 HTML 文件** | 未知 | **212** |

**87 个页面（41%）从未被审计。** 其中 83 个是 Hugo 生成的 `/page/1/` meta-refresh 别名页，
1 个是 `404.html`，其余是 sitemap 之外的 term/归档页。根因：sitemap 是 **SEO 索引**，
页面可以通过 `sitemap.disable` 把自己排除 —— 这类页面真实存在，却完全不在"全站"统计里。

### 修复

新增 `tools/html_inventory.py`：

- 递归扫描 `public/**/*.html`，规范化为 URL
  （`index.html → /`，`about/index.html → /about/`，`404.html → /404.html`）
- URL 统一 percent-encode —— 中文路径直接交给 `urlopen` 会抛 `UnicodeEncodeError`
  （本轮实测踩到：83 个别名页全部抓取失败）
- 分类仅用于报告，**不排除任何页面**：`site` 128 / `alias` 83 / `error` 1
- 排除项必须显式登记并打印，当前为空

`audit.py` FULL 模式：

- 审计 URL = inventory 真值 ∪ sitemap 独有 ∪ 新发现分页
- 硬断言 `EXPECTED == AUDITED`，任一差集即 `exit 1`
- 报告额外打印双向差异："仅在 sitemap" 与 "在构建产物但被 sitemap 排除"（当前 90 个）

## 二、分页发现：失败不再静默

### 问题

旧实现在 `urlopen` 异常时 `continue`，因此可能出现：

```
fetch failed + 队列空 + exhausted=True + PASS
```

### 修复

- 每个 URL 至少重试 2 次（`DISCOVERY_RETRIES=2`，总计 3 次尝试）
- 记录 `discovery_attempts` / `discovery_retries` / `discovery_failures`（含 URL 与异常）
- `exhausted` 仅在「队列耗尽 **且** failures == 0 **且** 未达安全上限」时为 `true`
- FULL 模式下 failures 非空 → 直接 `exit 1`
- 重试逻辑放在 `discover_pagination` 层，**注入的假 fetch 也被覆盖**，语义可被真实验证

### 四场景测试（`tools/test_pagination_retry.py`，13/13）

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 正常分页 | 4 个分页页全发现，零失败 | 4 个，retries=0，exhausted=True |
| 第一次失败第二次成功 | 重试救回 | retries=1，failures=0，exhausted=True |
| 前两次失败第三次成功 | 重试次数足够 | retries=2，failures=0，exhausted=True |
| **所有重试均失败** | **exhausted=False** | attempts=3，failures=1，**exhausted=False** |

## 三、HTML quality 与 audit 交叉验证

两者共用 `html_inventory` 模块与同一套 URL 规范化：

- `check_html_quality.py` 输出 `PUBLIC HTML FILES` 并落 `tools/html_inventory.json`
- `audit.py` FULL 读取该 json 比对，任一不一致即 `exit 1` 并打印双方差异
- CI 中 Release job 会先生成 inventory 再跑审计（该 job 独立 checkout）

这样以后新增 HTML 输出模板时：HTML quality 能发现、Release audit 也自动覆盖，
**任意一套漏掉都会 CI 红**。

## 四、安全基线（`tools/security_baseline.py`）

仅标准库，扫描构建产物 HTML + 主题源码：

`javascript:` / `vbscript:` / `data:text/html`、空 `href`、`target=_blank` 缺 `noopener`、
inline event handler、非预期外部 `script src`、非预期 `iframe`、非预期第三方域名、
危险 JS API（eval / document.write / new Function / innerHTML 拼接）、
`markup.goldmark.renderer.unsafe` 配置。

白名单全部可见打印并附豁免理由（已转义拼接 5 处、行级白名单 1 处）。

**修复一处真实加固点**：搜索结果渲染把 `it.url` 直接拼进 `href`，现改为 `esc(it.url)`。

## 五、文档一致性门禁（`tools/check_docs.py`）

- README 不得回退为"零外部 CDN 请求"这类绝对化表述
- 必须说明「默认无外部 CDN / 启用可选评论统计后加载第三方资源」
- 必须列出 giscus / Waline / Twikoo / Disqus / busuanzi 五个服务并说明默认关闭
- CHANGELOG 必须含当前版本条目

> 这条门禁在本轮**抓到了我自己**：README 更新日志里为描述该门禁而引用了被禁短语。
> 由此增加"引用豁免"机制 —— 引号包裹且带"防止/回退/绝对化"等元语境时豁免但打印，
> 声明式使用仍判红。修复后复验注入 F 仍 `exit 1`。

## 八、发布验证过程中修掉的三个真实问题

Release 门禁在前三次 tag CI 中各暴露一个问题，都做了根因修复而非放宽阈值：

| 次序 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 第 1 次 `37771885372` | webkit browser-tests 报 1 张 `hugo.svg` 未完成 | 快速滚动（40ms/步）让 webkit 来不及发起懒加载 | 复查前逐图 `scrollIntoView` 驻留 90ms |
| 第 2 次 `37774455199` | chromium Release 报 1 张图未完成 | CI 负载高，16/32s 预算偶发不足 | 复查轮次 2 → 3（加 64s 轮）、驻留 150ms、新增 `[slow-settle]` 诊断 |
| 第 3 次 `37776642893` | chromium Release 再报 1 张图未完成，`[slow-settle] 122s pending=1` | **预算用尽仍未完成 → 不是预算问题**：DWELL 之后又执行快速滚动，把刚进入视口的图片滚出视口，chromium 随即取消懒加载 | 复查轮次内改为 `DWELL → 直接等待预算`，不再插入快速滚动 |

第 3 次的诊断输出是关键证据：预算全部用尽仍失败，说明请求根本没在进行，
继续加预算毫无意义 —— 必须消除"滚出视口"这个动作。

**每次修复都做了双向验证**（不能只证明"不再误报"）：

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 正常页 | `settle = 0` | 0（1s 收敛） |
| 注入真实挂起图片（端点永不响应） | 仍判缺陷 | 1（121s 暴露） |

判定标准始终未变：所有轮次结束后仍未完成的图片照样判缺陷。代价是真实缺陷
暴露需要约 2 分钟 —— 这是"不掩盖缺陷"的合理成本。
